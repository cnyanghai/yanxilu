# 研习录 · 版本 2 · 总体方案（2026-10-29）

用户问了五个根本问题：程序设计走 kriss 的路还是农场视频的路；一层层叠还是小镇式铺开；都市简约还是魔法书院；是贴图、游戏引擎还是别的；要不要请顶尖架构师。这页把答案和理由写在一起，之后所有子文档（BRIEF、V2-ROADMAP、KRISS-ANALYSIS、INTERACTION）都服从它。

## 1. 程序设计风格：kriss 的运行时，农场视频的生产线

两者不是同一个层面的东西，所以不用二选一：

- **kriss 是运行时的样子**：场景是一份提前做好的资产，程序只管三件事：镜头（路由即机位）、交互（热点、卡片）、HTML 叠层（文字全在二维）。没有引擎、没有实时光、没有物理。
- **农场视频是资产的生产线**：参考图 → AI 出模型 → Blender 组装、打光、动画 → 渲染。它不是一个"程序"，它是做资产的流程。

我们的结构定为三层，每层各有一个"唯一来源"：

| 层 | 做什么 | 工具 | 唯一来源 |
|---|---|---|---|
| 资产层（离线） | 建筑壳、主角家具、风格包；烘焙三套光 | gpt-image-2 / Grok 出图，fal 上的 Rodin 或 Hunyuan3D 出模型，Blender 收拾与烘焙（`tools/blender/`） | `study_scene.py` 的尺寸、槽位、机位；`world/assets/` 的产物 |
| 世界层（配置） | 有哪些间、每间有哪些槽位、槽位绑什么数据、机位在哪、风格包是哪套 | JSON（`study.json` 是雏形） | 每间一份配置 |
| 运行层（网页） | 加载壳、按数据长出书 / 盒 / 牌 / 文竹、镜头与路由、点选与卡片、阅读器 | three.js 自带、无框架、importmap；阅读器复用版本 1 | `world/world.js` |

一句话：**资产像电影一样离线做，世界像游戏一样用数据描述，运行像网页一样轻。**

## 2. 一层层叠还是小镇：小镇式，横向铺开

- 院子里一间一间加（花房、宠物间、收藏室……），每间是独立单元：独立配置、独立资产包、独立加载、可独立换风格包。加一间就是院子里多一块地基，总览镜头不变。
- 不做 kriss 那种多层楼的纵向叠加：纵向叠加逼所有房间共用一种建筑语言，剖面要处理楼板遮挡，总览机位也要随层数变。
- 某一间内部可以有楼（比如藏书楼两层），那是这间自己的事，不影响院子。
- 总览是"院子"而不是"地图"：有边界、有路、有空地，空地就是未来的间。一个人的小世界不该是无限的城市。

## 3. 风格：先一种，机制留两种

- **主线是一种**：纸木墨铜的沉静书房，方向是概念图 B（墨色家具、花格窗、纸白墙、浅木地板）。这是研习录的身份，和 kriss 的粉彩黏土、农场的卡通低模都不同。
- **"魔法书院"不是第一种**，原因两条：它的识别度来自别人的 IP，照着做要么侵权要么像山寨；它需要大量道具和光效（烛火、飘书、符文），资产量是中式书房的几倍。但它可以是以后的风格包之一，叫"古典学院"或"藏书塔"，不叫哈利波特。
- **都市简约**也不是：它和"养"的气质相反，简约到没有东西可养。
- 风格包的机制从第一天就留着（建筑壳、家具套、三套光是可替换的一组），但第二种风格要等第一间做到位再开。
- 出图分工：整体概念图和逐件细节图都优先 **gpt-image-2（fal）**，因为它能把参考图喂进去保持风格一致；**Grok** 用来自由探索和出备选。按规矩，提示词和模型先给用户过目。

## 4. 是贴图、游戏引擎、还是什么：烘焙的三维

三种做法的谱系：

1. **预渲染图片**（暗黑二代的精灵图、很多"伪三维"网页）：只有图，镜头不能动，数据物件不能变。
2. **烘焙的三维**（kriss、Bruno Simon 的房间、我们）：几何是真的三维，光是提前烘进贴图的，运行时不算光；镜头能动、能视差、能点选；数据物件实时生成。
3. **实时引擎**（原神、燕云、Unity / Unreal / Godot 导出的网页）：实时光照、物理、角色、碰撞；重、费电、手机难。

我们是第二种，理由：每天打开、手机为主、国内网络、没有美术团队、不需要物理和角色。three.js 是 WebGL 库不是游戏引擎，正合适。和第三种的边界：以后要"活物"（猫、鱼）也用程序化动画和烘焙，不上物理引擎。

## 5. 要不要请顶尖架构师：不需要架构师，需要一位美术

- 架构已经不是瓶颈。三层结构、烘焙管线、镜头系统、数据驱动的槽位，这些在过去两天都跑通了，和 kriss 的做法同源。再请人来，产出也是一份类似这页的文档。
- 真正的瓶颈是**资产**：造型、材质、光的品味。最值钱的外援是一位三维美术师，做两件事：把第一间书房的主角家具做到位（或把 AI 出的模型收拾到位）；做一次 look-dev，把光和材质调到目标图的水平。按件计，几千元量级。
- 其次值钱的是**色彩脚本和目标图**本身，现在可以由 AI 出图加用户判断完成，不必请人。
- 如果想要一轮正式的"架构评审"，可以用 AI 分角色做（引擎架构、WebGL 创意技术、美术指导、产品）。它能查漏补缺，不能替代美术师的手。

## 6. 由此定下的流程

1. 目标图与色彩脚本（gpt-image-2 为主，Grok 为辅；先过目再出）。
2. 资产：建筑壳用 bpy 按目标图改造型；主角家具逐件出参考图 → fal 的 Rodin / Hunyuan3D → Blender 收拾 → 进槽位；细薄的东西程序化。
3. look-dev：Blender 里对着目标图调光和材质到像为止。
4. 烘焙三套光，进 `world/assets/`。
5. 运行层：接真实数据（第 4 步）、取书 / 开书 / 展开的交互（`INTERACTION.md`）、房色与卡片。
6. 第二间（花房）、风格包、开门，按 `V2-ROADMAP.md` 后半段。
