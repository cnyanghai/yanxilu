# 研习录 · 版本 2 路线图（立体化）

写于 2026-10-28。这页是版本 2 的立项分析：参考怎么拆、现在的样机差在哪、几个专业视角怎么看、一步一步怎么做。气质和已定的设计决定仍以 `BRIEF.md` 为准，这页不推翻它，只决定怎么把它做成真正的三维空间。

## 0. 版本划分

- **版本 1 系列**：现在上线的书架 + 档案架网页（`index.html` / `server/index.html`，`src/app.js` 全部逻辑）。保留，以后接着开发。在 git 上打了标签 `v1`，以后要给版本 1 修东西，从这个标签拉分支即可，主线 main 不受影响。
- **版本 2 系列**：同一份数据、同一套规矩，换一个三维的壳。目标不只是"一间书房"，而是"一个人的小世界"：书房是第一间，以后有花房、宠物间、手工间、收藏室；风格可以换（中式、古典、树屋、霍比特人）。
- 两个系列共用数据层（`S.data` 与 Baba 的 `/api/yxl/*`）和阅读器（读文章、读书仍是二维页面，三维里不读正文）。版本 2 在仓库里是独立目录 `world/`（服务器版路径 `/world`），版本 1 的 `index.html` 继续当主入口，直到版本 2 能完整替代它。

## 1. 两个参考拆解（2026-10-28 实地看过）

### igloo.inc（Abeto × Bureaux，Awwwards 年度级）

看到的：整站只有一个主角，一座冰屋。进场是灰蓝雾里的一个点，滚动时先长出蓝图式的线框和编号，再长出面，再长出体积和光，再变成有质感的冰。镜头围着它慢慢推拉，背景是无尽的三角网格地面。一屏只有这一件东西，文字很少。

拆出来的做法：

- **一种材质做到极致**：冰。所有视觉资产都是这一种材质的变体。
- **滚动即镜头**：滚动条不翻页，驱动一条镜头轨道和一条物体生长时间线。
- **UI 画在场景里**：编号、线框、文字都是场景的一部分，不是浮在上面的 HTML。
- **技术栈**（Awwwards 案例研究）：Three.js、three-mesh-bvh、Svelte、GSAP、Vite；建模 Houdini + Blender。自研了浏览器内实时调参、体数据导出压缩、程序化冰块生成器。性能上持续在低端机上实测，开场动画是代码和着色器生成的，不是视频。

对我们的意义：它证明了"一个概念做到底"的力量，也证明了代价。igloo 是一支专业团队的展示页，只有三个章节，不承载每天要用的功能。我们学它的纪律（一种材质、一个镜头、装饰承担信息），不学它的规模。

### kriss.ai（Studio 28K，Awwwards 案例研究 2024-12）

看到的：首页是粉色天空里的一座剖开的两层楼（dollhouse 剖面），云在飘。点"Learn More"，镜头走近，打字机式文字讲一句故事。到 `/home/overview` 是整栋楼的剖面总览，八间房各有一个加号热点。点热点或滚动，镜头飞进那间房（URL 变成 `/home/consultation-room`、`/home/surgery-room`、`/home/doctors-office`），左侧出现一张半透明卡片写这间房是做什么的，右下角有"总览 / 上一间 / 下一间"三个按钮。每间房是一个完整的小场景：家具、人物、窗、灯，风格是柔和的黏土质感。

拆出来的做法：

- **房间即单元，楼即总览**：一个 URL 一间房，总览是剖面楼。这正是我们要的"一间一间养"的结构。
- **镜头走近是唯一的导航**：没有菜单页，上一间下一间是镜头移动。
- **卡片贴在房外**：说明文字是 HTML 卡片，不在三维里排字，省了大量功夫。
- **技术栈**（案例研究）：OGL（比 Three.js 更小的 WebGL 库）、Svelte 5、Blender 建模、PayloadCMS、Cloudflare Pages + R2。流程是低保真草图和故事板，再细化，再做成 WebGL。

对我们的意义：这是版本 2 的结构样板。差别在于 kriss 的八间房内容是写死的宣传文案，我们的每间房里的东西是数据长出来的（几百本书、几十个盒、几百张牌），而且每天在变。

### 其它看过的

- **Bruno Simon《My Room in 3D》**（GitHub 4.5k 星，2021）：个人房间，Blender 建模，光照烘焙进贴图，Three.js 展示。这是"一间房"在网页上好看又跑得动的经典做法：场景里没有实时光，所有阴影都是 Blender 算好的。
- **flo-bit/room**（Svelte + Threlte，MIT，89 星）：浏览器里摆家具的小房间，用 Kenney / Kay Lousberg 的 CC0 家具套件。证明用现成低多边形套件能很快搭出可用的房间编辑器。
- **Rooms.xyz**（a16z 投，Apple 设计奖）：体素风房间搭建加小游戏，每个物件可以写 Lua。"房间是舞台，物件是道具"这句定义和我们一致。它走的是用户生成内容，我们走的是数据生成内容。
- **img2threejs**（19.6k 星，2026 很热）：用代码而不是模型文件重建物体。对我们那些本来就要按数据生成的东西（书、盒、牌、袋）是对的思路。

## 2. 现在的样机差在哪（`room/index.html`，CSS 3D）

截图看过桌面远景、桌面近景、手机晴窗三张。优点：材质纪律已经在（纸木墨铜），三景别和 Esc 后退可用，手机能开。差距：

1. **没有真的光**。灯是贴上去的两块径向渐变，书、盒、花盆都不投影、不受光。igloo 和 kriss 的立体感八成来自光和影。
2. **没有空气**。墙和桌是两张平面，没有深度雾、没有景深、没有环境遮蔽，拉近后像纸板模型。
3. **物件是贴片**。文竹是平面图，牌是一个 div。没有厚度就没有"可以拿起来"的感觉。
4. **CSS 3D 的天花板**：每本书是一个 DOM 节点，几百本书加上几十个盒已经让浏览器吃力（今天用 Chrome 扩展连着看 `/room` 时渲染进程卡死过一次，原因没有定论，但这是个信号）。弯曲的台灯罩、圆的花盆、叶子的卷曲，CSS 做不出来。
5. **只有一间**。没有"总览"这一级，加第二间房没有地方放。

结论：CSS 3D 完成了它的任务（验证构图和材质纪律），下一步必须换 WebGL。

## 3. 专家组分析

下面六个视角是分开推演的，每个给判断、建议和反对意见，最后汇总成决定。

### 视角一：创意总监（概念与风格）

判断：两个参考的共同点是"网站是一个地方，不是一叠页面"，我们的简报已经写了同样的话，方向不用改。要警惕的是 kriss 那种粉色黏土风很讨喜，但它是另一套材质宇宙。研习录是纸木墨铜、一盏灯，这套比黏土风更稀缺，也更配"养"这个动词。

建议：

- 总览不要做成 kriss 那样的"楼剖面"，做成**一座院子的鸟瞰**或**一张手绘宅图**。中式的"间"天然是院落式排布，每间房是一个独立的盒子，加一间就是在院子里添一间。风格包换的时候，换的是院子的建筑，不是布局。
- 首屏主角的两个候选（今天的牌 / 案头的文竹）里，三维化后**文竹更占优**：它是唯一会随时间长的物件，三维里的生长（新叶展开）比平面图动人得多。牌放在桌面第二位。这条还是等用户拍板。
- 风格包的清单先收口到两个：**中式书房**（现在的）和**一个反差大的**（霍比特人圆门土屋或树屋）。两个风格能跑通，第三个就是填数据。

反对意见（自己给自己的）：三维不等于好看。igloo 好看是因为克制到只剩一个物体。我们的房间里有几百样东西，第一版要敢于**把东西做少**：书墙只露最近在读的那一格清楚，其它格子虚掉。

### 视角二：三维技术负责人（引擎与渲染）

判断：引擎选 **Three.js 原生 + 不用前端框架**。理由：现有代码是无框架的单文件，团队（用户 + Claude）熟悉它；Three.js 文档和案例最多；R3F / Threlte 要引入 React 或 Svelte 整套工具链，收益不抵成本；OGL 更小但生态薄，kriss 用它是因为有专业图形工程师；Babylon 更大更全，我们用不上物理和多人；Needle、Spline、PlayCanvas 都绑定它们的云或编辑器，国内访问和长期可控性有风险；Godot 导出网页要 30 MB 的运行时，手机开不动。

渲染路线：

- **光照烘焙**（Bruno Simon 的做法）：房间的建筑和大件家具在 Blender 里打灯、烘焙到贴图，场景里不放实时光源，手机也能跑。三间房（夜读 / 晴窗 / 雨天）就是三套烘焙贴图，切换是贴图淡入淡出，正好对应简报里"切换只换光，东西不换"。
- **数据驱动的物件走程序化几何**：书、盒、袋、牌、叶子都是按数据生成的，不可能一件件建模。书是一个带圆角的长方体加 canvas 画出来的书脊贴图，用 InstancedMesh 一次画几百本；盒和袋同理。这部分不烘焙，用一盏低成本的半球光加预先算好的环境遮蔽贴图糊过去。
- **资产格式**：glTF，几何用 Draco 压缩，贴图转 KTX2（gltf-transform 一条命令），全部放 `vendor/` 自带，不走任何 CDN。
- **不打包**：用 importmap 引入 `vendor/three/` 的 ES 模块，继续用 `python3 build.py` 那套，不引入 Vite。等真的需要再说。

预算（第一版的硬指标）：

| 指标 | 桌面 | 手机 |
|---|---|---|
| 首屏资源 | 4 MB 以内 | 2.5 MB 以内 |
| 帧率 | 60 | 30 以上 |
| draw call | 150 以内 | 100 以内 |
| 书房单间三角面 | 30 万以内 | 15 万以内 |

反对意见：烘焙意味着"动一件家具就要重新烘焙"。所以要分清**建筑层**（墙、地、梁、窗、大书架、桌：烘焙，几乎不变）和**物件层**（书、盒、牌、植物、灯具小件：实时，随数据变）。可以搬动的只能是物件层。

### 视角三：交互与游戏设计师

判断：kriss 用滚动驱动镜头是因为它是一次性看完的宣传页。研习录每天打开，**点按走近、Esc 后退**（简报已定）比滚动更合适；滚动只用来在当前景别里微调远近。手机上双指缩放等于滚动。

建议：

- **四个景别，不是三个**：院子（总览）、整间房、一件家具、一件物。URL 一一对应：`/world`、`/world/study`、`/world/study/wall`、`/world/study/wall/<book>`。浏览器后退就是镜头拉远，和 kriss 一样可分享。
- **热点要少**：一间房里能点的东西不超过七个，远景时只亮正在"长"的那一两个（今天的牌、这周长叶的文竹），其它的要走近了才亮。
- **"养"的反馈必须看得见**：读完一篇，牌从桌上飞进盒里；连读一周，文竹冒一片新叶；一个月没碰的盒子落一层灰（灰是贴图叠加，不是红点）。这些动效每个都编码一个状态，符合"装饰必须承担信息"。
- 游戏感六分的来源不是粒子和光效，是**手感**：拿起一张牌有重量（缓动曲线）、翻过来有纸声、放回去会轻轻落下。先把这三个手感做对，比做十种动画值钱。

反对意见：三维里的文字可读性很差。所有要读的字（书名、盒名、说明）要么是贴图上的大字，要么是 HTML 卡片贴在屏幕边上（kriss 的做法）。不要在三维里排段落。

### 视角四：产品与养成系统

判断："一个人的完整小世界"这个愿景和用户 2026-07 提过的"智慧树型社交"（一棵树就是一个人，能走进别人的树）是同一个愿景的两种形态：树是时间线形态，院子是空间形态。版本 2 应该明确自己是这个愿景的空间形态，以后"走进别人的院子"就是那个"走进别人的树"。这条要让用户知道，免得两个项目各长各的。

建议：

- **"间"的抽象先于第二间房**。一间房 = 建筑（风格包决定）+ 若干家具槽位（固定）+ 每个槽位绑定一个数据集合（书墙绑 `books`，档案架绑 `aboxes` + `clips`，案头绑今天的牌和植物）。换风格只换建筑和家具的模型，槽位和绑定不变。这样第二间房、第二种风格都是填表。
- **第二间房选花房**，不选宠物间。理由：植物已经有数据来源（读书时长、连续天数），"养"的逻辑是现成的；宠物需要一整套行为系统（饿、睡、认人），是另一个项目的量。宠物间放到花房跑通之后。
- **空的第一天要好看**。新用户的院子只有一间空书房、一盆小苗、一张空桌，要有"这里等着我来养"的感觉，不要有"你什么都没有"的感觉。简报里"从第一天设计规模"这条在三维里更难，要专门做。
- 数据可导出为纯文本这条不变，三维层不持有任何独有数据，只持有"摆放偏好"（哪件摆件放哪格），这类偏好单独存，丢了也不心疼。

反对意见：在制品上限。brain 里现在已经有五个进行中项目，研习录一直没登记。版本 2 一开工就是第六个，按铁律要先暂停一个。这不是 Claude 替用户选的事。

### 视角五：性能、网络与设备

判断：目标设备是用户自己的电脑和手机，以及以后"进来看"的访客的手机。国内网络下，一切资源自带（已经是规矩）。WebGL 2 在 2026 年的手机浏览器里基本可用，微信内置浏览器也能跑 Three.js，但内存紧，纹理总量要控制在 64 MB 以内。

建议：

- 按房间分包，进院子只下总览所需的低模和一张总图；走进哪间下哪间。
- 低端设备和 WebGL 不可用时，自动落回版本 1 的平面界面，不是报错页。这也是版本 1 必须留着的硬理由。
- 每个镜头动作打点（已在简报里），加上首帧时间、掉帧率两个指标，一个月后拿数据决定要不要降模。

### 视角六：内容生产管线（谁来做模型）

判断：这是最大的现实风险。igloo 和 kriss 背后都有专职三维美术。我们没有。

建议分三层解决：

- **建筑和大件家具**：先用 CC0 低多边形套件（Kenney、Kay Lousberg 的家具包，flo-bit/room 就是这么起步的）搭灰盒，把镜头、槽位、光照烘焙的流程跑通；再决定是自己在 Blender 里重做中式家具，还是用 AI 生成（Tripo、Hunyuan3D 2.1、TRELLIS.2 都能出 glb，但出来的拓扑需要在 Blender 里减面和重新展 UV，一件家具半天）。
- **数据驱动的物件**：程序化生成，不需要美术。书脊、盒面、牌背的贴图是现在版本 1 已经用 canvas 画出来的东西，直接复用。
- **植物**：文竹的叶子用几片带透明贴图的曲面加骨骼式的生长参数，程序化做；这是全场最该精雕的一件，值得手工建。

规矩不变：不用任何暴雪美术，所有外来资产只收 CC0 或明确可商用的，来源记进 `REFERENCES.md`。

### 汇总：定下来的和没定的

定下来的（除非用户反对）：

| 事项 | 决定 |
|---|---|
| 引擎 | Three.js 原生，ES 模块 + importmap，自带在 `vendor/three/` |
| 框架 | 不引入 React / Svelte，继续无框架 |
| 渲染 | 建筑层烘焙，物件层实时 + 程序化几何，InstancedMesh 画书 |
| 导航 | 四景别，点按走近 / Esc 或浏览器后退拉远，URL 对应景别 |
| 结构 | 院子（总览）→ 间 → 家具 → 物；"间"是数据驱动的单元 |
| 顺序 | 书房先，花房第二，风格包第三，宠物与社交最后 |
| 资产 | glTF + Draco + KTX2，CC0 套件起步，程序化为主 |
| 版本 1 | 打标签 `v1` 保留，兼作低端设备的回退界面 |

等用户定的：

1. 首屏主角：**已定文竹**（2026-10-28），今天的牌放桌上第二位。
2. 第二种风格选哪个：霍比特人土屋还是树屋（或者中式之外先不做第二种）。
3. 建模分工：**已定 CC0 套件 + 程序化起步**（2026-10-28）。建筑和大件家具先用简单几何和 CC0 低多边形包搭灰盒，书、盒、牌、叶程序化生成，正式美术以后再说。
4. 在制品上限：版本 2 开工前先暂停哪个进行中项目。
5. 版本 2 和"智慧树型社交"的关系：是否认可"院子是树的空间形态"这个定位。

## 4. 分步路线

每一步有交付物、验收标准和止损条件。用户时间充足，这里不写周数，按步走，一步验收过了再走下一步。

### 第 0 步：封存版本 1，立版本 2 的架子

- 交付：git 标签 `v1`；`STATUS.md`、`REFERENCES.md` 建好；`world/` 目录和 `vendor/three/` 就位；Baba 那边加 `/world` 路由（另一个仓库，一条 route）。
- 验收：`https://baba.wogucloud.cn/world` 能打开一个空的 Three.js 画布，手机也能。
- 2026-10-28 完成：标签、文档、`vendor/three/`、`world/`、Baba 路由（待部署）。

### 第 1 步：一间灰盒书房，镜头先对

- 2026-10-28 第一版已写出，等用户验收。

- 交付：用 CC0 套件和简单几何搭出书房的建筑层（墙、地、窗、书架、桌、灯）；四景别镜头和 URL；三间房的光先用三组实时光凑合；一盆文竹的程序化叶子。
- 验收：桌面 60 帧、手机 30 帧；从院子点进书房再点到桌面再 Esc 回来，每一步镜头没有穿模、没有突兀；三个人看了说"是一间房"而不是"是一个网页"。
- 止损：如果两轮迭代后镜头仍然让人晕，退回简报重新定景别。

### 第 2 步：把版本 1 的数据长进来

## 5. 第一周能动手的具体事（等拍板后）
